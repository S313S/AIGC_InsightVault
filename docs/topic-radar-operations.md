# AI 创作者话题雷达：运行与验收

本文是运维契约，不把“代码已配置”“本地验证通过”“已部署”“生产已观测”混为一谈。每次交付都应分别记录这四种状态。

## 数据流与用户看到的含义

```text
X / 小红书（关注度） ─┐
                      ├─ 证据去重与聚类 ─ 评分与摘要 ─ 三个编辑队列
官方 RSS / GitHub（事实）┘
```

- **今日值得写**：近 72 小时内、写作价值达到阈值的话题，最多 5 条。
- **值得沉淀**：近 30 天内、可复用知识价值达到阈值的话题，最多 5 条。
- **突发雷达**：近 24 小时内、突发分达到阈值的话题，最多 3 条。
- 官方或仓库证据提高可信度，但不会凭空制造社交传播热度。
- 每个话题可展开查看事实来源和热度来源；原始帖子池仍保留用于核对。

## 定时与手动运行

`vercel.json` 当前配置为每天 `00:00 UTC` 执行一次 `/api/cron-monitor`，即北京时间每天 08:00（不考虑历史配置或平台侧覆盖）。Vercel 实际是否启用、最近一次是否成功，必须在部署后另行核对。

设置页的手动抓取会调用同一接口。一次运行完成后：

1. 先保存本次原始证据；
2. 再生成或更新话题投影；
3. 最后清理未被话题引用的旧热点快照。

话题生成或某个事实源失败时，已成功抓取的社交证据不会回滚；运行状态应显示为“部分失败”，并保留分来源错误。

## 环境变量

### 必需

| 变量 | 用途 |
| --- | --- |
| `SUPABASE_URL` | 服务端数据库地址 |
| `SUPABASE_SERVICE_ROLE_KEY` | Cron 的服务端写入凭证，只能配置在服务端 |
| `CRON_OWNER_USERNAME` | Cron 数据归属账号，默认 `xiaoci` |
| `X_API_BEARER_TOKEN` | X 搜索；若只启用小红书，可不配置 |
| `JUSTONEAPI_TOKEN` / `TIKHUB_API_TOKEN` | 小红书来源，至少配置一个才可抓取小红书 |

至少要有一个社交来源凭证；当前 Cron 在所有社交凭证都缺失时会直接失败，而不是退化为仅事实源运行。

### 话题摘要与事实源（可选）

| 变量 | 默认值 | 说明 |
| --- | ---: | --- |
| `GEMINI_API_KEY` | 无 | 生成话题摘要；缺失或失败时使用规则回退并标记“自动摘要/待核验” |
| `GITHUB_TOKEN` | 无 | GitHub Releases 鉴权；不配置时使用匿名限额 |
| `TOPIC_OFFICIAL_MAX_FEEDS` | `2` | 每次运行的官方 feed 数，范围 0–10；`0` 为停用 |
| `TOPIC_GITHUB_MAX_REPOS` | `3` | 每次运行的 GitHub 仓库数，范围 0–10；`0` 为停用 |
| `TOPIC_FACT_TIMEOUT_MS` | `6000` | 每个事实源 HTTP 请求超时，范围 1000–30000 毫秒 |
| `TOPIC_FACT_RECENT_DAYS` | `35` | 事实证据回看窗口，范围 1–365 天 |
| `TOPIC_FACT_MAX_ENTRIES` | `10` | 每个 feed/仓库最多读取条数，范围 1–50 |
| `TOPIC_FACT_MAX_PAGES` | `1` | GitHub 每仓库最多分页数，范围 1–3 |
| `TOPIC_FACT_MAX_RESPONSE_CHARS` | `1000000` | 单响应大小上限，范围 10000–5000000 字符 |
| `TOPIC_FACT_MAX_CONTENT_CHARS` | `4000` | 单条正文保留上限，范围 256–20000 字符 |

生产默认来源由服务端代码中的 curated allowlist 固定。自定义 feed 只应来自受信的服务端配置；若未来允许用户提交域名，必须先增加 DNS 解析后的私网与重绑定防护。

## 数据库迁移顺序

在现有数据库上依次执行：

1. `scripts/supabase-auth-rls.sql`
2. `scripts/cron-run-logs.sql`
3. `scripts/topic-radar-schema.sql`

第三步会增加 `topics`、`topic_sources`、`topic_feedback`、索引、约束、RLS 策略及安全删除 RPC。应用部署前先做只读检查，确认表、索引、约束和 RLS 均存在。不要因为前端能打开就认定迁移成功。

## 运行状态

| 状态 | 含义 | 操作建议 |
| --- | --- | --- |
| `healthy` | 所有计划来源完成并产生候选 | 检查话题数量与证据质量 |
| `healthy_low_volume` | 所有计划来源完成，但筛选后为 0 条 | 检查当天是否确实低量，再看关键词/阈值 |
| `partial_failure` | 至少一个来源完成，同时有来源或下游步骤失败 | 可使用已保存结果；查看 `platformErrors` |
| `failed` | 没有计划来源有效完成 | 不应把旧内容称为“今日新热点” |
| `truncated` | 触发运行时保护，未完成全部计划工作 | 降低任务数或调用上限后重跑 |
| `skipped` | 自动更新关闭或处于仅重建模式 | 核对 `skipReason`，无需误报故障 |

`platformTotals` 记录各来源的抓取数、输出数和完成调用数；`platformErrors` 只保存安全错误类别和来源标识，不保存 Token 或上游响应正文。

## 两种“新鲜度”

- **热点采集时间**：最近一次成功获得热点快照的时间，决定内容是否过期。
- **页面同步时间**：当前浏览器最近一次从云端刷新成功的时间，只说明页面是否同步，不代表后端刚采集。

有缓存时页面先展示上次成功内容，再在后台同步；采集过期时继续保留旧内容并显示明确提醒。不要用“刚刚同步”替代“刚刚采集”。

## 本地验收

```bash
npm test
npm run build
git diff --check
```

还需用确定性 fixture 核对：写作/学习队列各 3–5 条、突发不超过 3 条、每条有可展开证据链接、一个来源失败时状态为 `partial_failure`，并且热点采集时间与页面同步时间分开显示。

这些检查只证明本地代码状态。它们不证明 SQL 已应用、分支已推送、Vercel 已部署或真实外部 API 已成功运行。

## 回滚边界

- **事实源快速停用**：将 `TOPIC_OFFICIAL_MAX_FEEDS=0` 和/或 `TOPIC_GITHUB_MAX_REPOS=0`，社交采集仍可继续。
- **应用回滚**：回退到上一已验证部署；不要同时删除数据库表。
- **数据保全**：话题投影失败时不删除原始卡片；只有投影完整后才运行引用感知的旧快照清理。
- **Schema 回滚**：本次迁移是增量结构。未经备份与引用检查，不要删除表、策略或证据关系。
- **正式验证成本**：生产只做一次经授权的低成本手动运行；之后至少观察连续 3 次日更，才能评价稳定新鲜度。
