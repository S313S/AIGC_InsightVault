# 收藏夹独立加载设计

## 背景

知识卡片列表为了控制首屏请求量，只加载按 `created_at` 倒序排列的前 60 条；收藏夹计数则扫描全部知识卡片。当前收藏夹页面直接在这 60 条卡片中做本地过滤，因此较旧的收藏条目仍存在于 Supabase、左侧计数也正确，但进入收藏夹会显示 0 条。

## 目标

- 进入收藏夹时直接读取该收藏夹的真实条目，不依赖首页已经加载的分页。
- 兼容同名收藏夹历史记录聚合出的多个收藏夹 ID。
- 明确区分加载中、加载失败和确认空收藏夹，避免把网络失败误报为数据为空。
- 收藏夹读取不改变首页分页偏移，避免首页“加载更多”跳过卡片。
- 快速切换收藏夹时，较早请求的返回结果不能覆盖当前收藏夹。

## 方案选择

采用收藏夹独立查询。首次加载全部知识卡片会随数据增长拖慢首页；仅在空页面暴露“加载更多”仍需要用户手动翻页，也无法保证计数和内容一致。

## 架构与数据流

### 数据服务

在 Supabase 服务层增加收藏夹专用只读方法：

1. 接收一个或多个收藏夹 ID。
2. 清理和去重 ID；空输入直接返回空数组。
3. 使用数组重叠条件查询 `knowledge_cards.collections`。
4. 只选择列表所需字段，按 `created_at` 倒序。
5. 分页读取直至不足一页，避免未来单个收藏夹超过服务端单页上限时再次出现截断。
6. 查询错误向调用方抛出，使界面能够区分“查询失败”和“确实为空”。

Supabase 的 RLS 继续负责访问控制，不扩大现有数据权限。

### 页面状态

收藏夹使用独立的 `collectionCards`、加载状态和错误信息，不把查询结果合并进首页 `cards`。这是为了保持首页分页 offset 只代表已加载的首页页数。

点击收藏夹时：

1. 取得该收藏夹的全部别名 ID。
2. 清空旧错误并进入加载状态。
3. 发起收藏夹专用查询。
4. 通过递增请求编号忽略过时响应。
5. 成功后显示真实条目；失败后保留明确的失败状态和重试入口。

关闭收藏夹或切换主导航时，取消当前结果的展示并使未完成响应失效。

### 现有交互同步

收藏夹卡片仍支持详情读取、更新、删除、批量移出和收藏夹对话。上述操作同时更新独立的收藏夹状态；首页卡片状态只在对应卡片已经存在时同步更新。

## 界面状态

- 加载中：显示“正在加载收藏夹内容”，不显示空状态。
- 加载失败：显示错误说明和“重新加载”按钮，不显示“收藏夹为空”。
- 成功且为零：显示确认后的空收藏夹状态。
- 成功且有数据：标题数量取当前完整查询结果，卡片正常展示。

## 测试策略

- 服务查询测试：验证使用数组重叠条件、多个别名 ID、列表字段、排序和分页。
- 页面结构回归测试：验证收藏夹点击触发独立读取，使用独立状态，且有加载、失败、重试和过时响应保护。
- 交互同步测试：验证详情更新、删除和批量移出会同步收藏夹状态。
- 全量验证：运行全部 Node 测试与生产构建。

## 不在本次范围

- 不改变首页 60 条分页策略。
- 不调整 Supabase 表结构或 RLS。
- 不部署、不推送远端，也不修改云端数据。
